# Phase 4: Story Evolution

Phase 4 让系统从“每天重新聚类”升级为能够识别事件演进的持续情报系统。

## Continuity

每次生成简报时，系统会将当前事件与最近七天的历史故事进行匹配：

1. 优先检查已关联文章 ID，稳定识别重叠窗口内的同一事件。
2. 没有文章重叠时，使用标题、实体、主题和时间间隔识别后续报道。
3. 匹配成功后沿用原 `story_key` 和首次出现时间。
4. 同一个历史故事在单次处理中只会被一个当前事件认领，避免错误合并。

该逻辑完全在本地运行，不依赖 embedding 或外部模型。

## Status

故事包含以下状态：

- `new`：首次识别的新事件。
- `developing`：历史故事出现了发布时间更晚的新报道。
- `ongoing`：当前窗口仍包含该故事，但本轮没有新增报道。

同时记录：

- `updateCount`：故事被确认出现实质更新的次数。
- `newArticleCount`：本轮相对历史故事新增的文章数量。
- `previousLastSeenAt`：上次已知更新时间，仅用于本轮展示。

## Experience

HTML 和 Markdown 简报会展示中英文状态、追踪次数和本轮新增报道数。
发展中事件额外展示上次已知进展和最近四条报道组成的时间线，即使当前窗口只有
一篇新跟进也能保留前后关系。

Dashboard 新增：

- 发展中事件指标。
- “正在发生”快捷筛选。
- 每个事件的状态、追踪次数和新增报道数。

## Migration

`init-db`、`run`、`brief` 和 `serve` 启动时都会执行幂等迁移，为旧数据库的
`stories` 表增加 `status` 与 `update_count`。无需删除现有 `data/news.db`。
